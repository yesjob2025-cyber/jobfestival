개인 업무 · 시간관리 웹앱. 단일 HTML 파일 + Supabase + Google Apps Script 두 개로 이뤄져 있다.
이 문서 하나로 구조 · 규칙 · 남은 일을 파악할 수 있게 정리했다.

## 2. 데이터 모델 (`plans.data` = 앱의 `ST`)

```js
{
  log:   { 'YYYY-MM-DD': [itemId, ...] },      // 체크한 루틴 항목
  reps:  { 'YYYY-MM-DD': { itemId: n } },      // 반복 항목 횟수 (2 이상만)
  rec:   { 'YYYY-MM-DD': { itemId: value } },  // 기록. value = string | string[] | [{t,s,u,star}]
  extra: { 'YYYY-MM-DD': { 블록: [{id,n,a,m}] } }, // 그날만의 '기타' 항목
  routine: { wd:{아침:[item...],오전:[],오후:[],저녁:[]}, sat:{...}, sun:{...} },
  todos: [{ id,t,cat:'업무'|'개인',lv:'중요'|'일상',pid,ph,done,doneAt,u,tpl }],
  gone:  { todoId: ts },                       // 삭제 기록(묘비)
  picks: { 'YYYY-MM-DD': [todoId,...] },       // 그날 고른 할 일
  weekNote: { '주시작일': '메모' },
  tpls:  [{ id,name,cat,items:[{t,lv,ph}] }], tplVer,
  books: [{ id,t,a,pub,pg,cur,cat,st:'d'|'r'|'w'|'x',start,end,yr,rate,memo,u }],
  rdg:   { 'YYYY-MM-DD': { itemId:{b:bookId,p:page} } },
  bookGoal, bookSeed, allRead,
  info:  [{ id,type,t,s,u,star,lens,tg,src,d }],   // 보관한 정보
  infoStar: { 'day|itemId': 1 },                   // 글 기록형 정보의 ⭐
  inbox: [{ id,d,type,lens,topic,tg,t,s,u,src,q,at }],  // 자동 수집 (최대 50)
  inboxDone: { inboxId: ts },                      // 보관·버림 처리 기록
  collectedAt,
  prayers: { morning, evening, salve }, prayFz,
  stage, used
}
```

**루틴 항목 구조** `{ k(고정키), n(이름), a(영역), m(분), p(점수), rep?, pray?, todo?, note?, rec? }`
`itemId = 요일번호 + '-' + 블록 + '-' + (k || n)` — **이름을 바꿔도 k 가 유지돼 과거 기록이 이어진다.**

**영역 → 점수 묶음** `GROUP = {신앙:영성, 건강:운동, 성장:성장, 업무:일, 마음:성장}`
**할 일 점수** 중요 2점 · 일상 1점(상한 없음), 만점 계산에는 중요 3 · 일상 6 기준이 들어감.
**목표선** 만점의 62%, **보상선** 85%.

## 4. 반드시 지킬 규칙

1. **저장 키 `daily-plan-v11` 을 바꾸지 않는다.** 바꾸면 로컬 기록이 끊긴다.
2. **데이터 구조를 바꿀 때는 `normalize()` 에 마이그레이션을 넣고 `_dirty=true` 로 저장을 유도**한다. 항목 이름 변경은 `migrate()` 의 NAME/GONE 표에 추가.
3. **루틴 항목의 `k` 를 바꾸지 않는다.** 과거 체크 기록이 끊긴다.
4. **서버 저장은 항상 병합 후**(`cloudPut` 이 `cloudGet`→`mergeTodos` 실행). Apps Script 가 같은 행을 건드리므로 통째로 덮어쓰면 안 된다.
5. **단일 파일 유지.** 외부 스크립트는 supabase-js(UMD) 하나뿐. 폰트는 CDN.
6. **UI 문구는 한국어**, 존댓말, 간결하게. 이모지는 최소.
7. **민감정보는 앱으로 들이지 않는다.** 업무 시트의 계좌 · 주민번호 · 강사 연락처는 동기화 대상에서 제외.
8. 기도문 본문은 사용자가 직접 넣은 개인 사용본. 배포용 코드에 다른 저작물 본문을 추가하지 않는다.

## 5. 배포 · 테스트

**배포** 브랜치에서 `public/funnyrak/index.html` 수정 → `npm test` → PR → `main` 병합 → Vercel 자동 배포(2~3분) → 앱 새로고침.
Apps Script 는 `funnyrak/gas/` 에서 수정 → `clasp push` (설정은 `funnyrak/README.md` 5번).

**테스트** `cd funnyrak && npm test` — GitHub Actions 에서도 자동 실행.
- `test/app.test.js` 앱을 jsdom 로컬 모드로 띄워 규칙 1·3·4·5, 기록 보존, `mergeTodos` 확인. 도우미 `test/load-app.js` 의 `loadApp(seed)` → `w.eval('ST')`
- `test/gas.test.js` Apps Script 서비스를 mock(`test/gas-env.js`)하고 `plans.data` 를 메모리(`env.db.data`)로 바꿔 wsync · wcollect 실행
- 기본 루틴 `k` 목록은 `test/fixtures/routine-keys.json` 에 고정. 의도한 변경이면 `migrate()` 와 함께 고친다.

## 6. Apps Script 두 개

**`sheet-sync.gs` (wsync)** — 시트 `주간업무` 탭 ↔ `todos` 양방향.
- `wsyncSetup` 설치(기존 트리거는 건드리지 않음), `wsyncPull`(5분마다), `wsyncOnEdit`(즉시 push), `wsyncPush`
- 업무(cat='업무')만 다룸. 개인 할 일은 시트에 나오지 않음
- 줄 삭제 대신 '삭제' 체크박스 사용. 행 매칭은 ID 열

**`info-collect.gs` (wcollect)** — 구글 뉴스 RSS + 정책브리핑(korea.kr, site: 검색) 수집 → `inbox`
- `wcollectRun`(지금 수집), `wcollectSetup`(매일 07:00 · 09:00 트리거 생성 → `wcollectDaily`), `wcollectDaily`(그날 이미 수집했으면 건너뜀 — 9시는 7시 실패 대비), `wcollectCheck`(트리거 · 앱 연결 · 마지막 수집 · 오늘의 전문지 점검), `wcollectReset`(inbox 비우고 다시 안 들어오게 표시)
- 구성: **키워드 뉴스 중심**, 전문지는 **하루 한 곳씩 순환**(`MEDIA` 순서, 한국 날짜 기준 `날번호 % 7` → 매체마다 주 1회, 지난 7일치 최대 10건), 정책·연구기관은 소량
- 기간: 뉴스·보도자료·연구기관 24시간 / 전문지 7일
- 하루 자리: 뉴스 30 · 전문지 10 · 보도자료 5 · 연구기관 5 (모자라면 서로 채움), inbox 최대 50
- 중복 제거: id(링크 해시) · 제목 정규화 · 기존 info 의 링크 · inboxDone
- 설정은 파일 상단 `WCOL` 한 곳에서 수정

## 7. 남은 일 (우선순위 순)

1. **입찰 자동 수집** — 공공데이터포털 '나라장터 입찰공고' API. 키워드 필터 후 `inbox` 에 `type:'입찰'`. 카드에 '제안 준비' 버튼 → `사업준비(제안)` 템플릿으로 주간 보드 생성(공고명·마감일 포함)
2. **AI 요약** — Supabase Edge Function 에 Anthropic 키를 숨기고, 앱에서 호출. ⭐ 보관한 기사 → "제안서에 쓸 두세 줄" 요약, 기록 다듬기
3. **사업총괄 시트 연동** — 고유번호(C251026_01 형식)로 앱 사업 ↔ 시트 행 연결. 사업형태(A.교육/B.온라인/C.행사) → 업무 유형 자동 선택, 드라이브 사업 폴더 열기, 진행(1.준비/2.결과/3.정산) 갱신 제안
4. **통계 노트** — 정보함에 숫자 한 줄 형태(수치·시점·출처) 보관과 모아보기
5. **주간 정보원 훑기** — 연구기관 보고서 원문 등 '사이트·자료' 고정 목록과 금요일 체크
6. **팀 확장 대비** — 업무 데이터만 별도 테이블로 분리, 연동 전용 계정, 담당자 필드

## 8. 사용자 맥락 (판단 기준)

- 취업·진로·박람회·연수 제안서를 자주 쓰는 1인 운영. 앱은 개인용이며 혼자 쓴다.
- 계획을 크게 세우면 실행이 무너진 경험이 있어, **항목 수를 늘리는 방향의 제안은 신중히**. 기본은 "적게, 확실히".
- 매일 여는 것이 성공 기준. 기능 추가보다 여는 부담을 줄이는 쪽을 우선한다.
- 기록이 끊기면 의욕이 크게 꺾인다. 마이그레이션 · 백업('백업·계정' 시트)을 항상 함께 고려할 것.
